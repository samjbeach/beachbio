Autonomous wiki — architecture

immutable markdown sources · Hermes agent via OpenRouter · Postgres + pgvector wiki (Supabase)

The site is a front end for LLM conversations and deep research. Every session's markdown output lands in cold storage as immutable truth — write-once, never edited. A Hermes agent (via OpenRouter) reads those sources on its own and folds them into a living wiki held in Postgres: pages, backlinks, tags, embeddings. The wiki is hands-off — the agent maintains it without you in the loop — and that's only safe because it is a rebuildable projection of sources the agent can never touch.

Two tiers, one direction

This is an append-only source log feeding a derived read model — the same shape as event-sourcing / CQRS. The truth is the log of raw markdown; the wiki is a view over it.

Load-bearing decisions

the safety net

Sources are immutable — enforced structurally, not by trust

The agent holds a read-only credential to the source store. It cannot rewrite the record even if it wanted to. Everything downstream is recoverable because this one thing can't be corrupted.

why it's safe

The wiki is rebuildable, therefore disposable

Because the wiki is derived from immutable sources, a rogue run can't cause irreversible loss. Worst case you re-run the derivation. Test a full rebuild periodically so this stays true, not just theoretically true.

hands-off, not blind

Auto-merge with history — not a human gate

The old plan gated every edit on a PR you merge; hands-off drops the human, not the audit trail. Every agent edit is a diffable revision (page_revisions or a git commit) that auto-applies — you can audit and revert any run after the fact.

machine gates

Cheap tripwires stand in for the reviewer

With no human per-edit, put automated checks between agent and wiki: reject a run that deletes >X% of content, guts a heavily-linked page, or leaves dangling links. Never hard-delete — archive/supersede so nothing is truly gone.

provenance

Every claim links back to its source

A page_sources join ties each wiki page to the immutable markdown it was built from. "Why does it say this?" is always answerable, and corrections/rebuilds stay tractable because the lineage is explicit.

right store per job

Postgres for the graph, blobs for the prose

A wiki's value is its connections — backlinks, tags, search — which are relational, so Postgres is the strong pick (with pgvector, RAG lives in the same DB). Cold markdown is write-once blobs; that's not Postgres's job.

Data model

Tier 1 is one append-only table (or a bucket). Everything else is tier 2 — the agent's workspace, all rebuildable.

-- tier 1: the record — append-only, agent is READ-ONLY
sources        (id, created_at, kind, title, body_md, meta)

-- tier 2: the living wiki — agent read/write, all rebuildable
pages          (id, slug, title, body_md, embedding vector, updated_at)
page_revisions (page_id, rev, body_md, changed_at, run_id)   -- history / revert
links          (from_page, to_page)                          -- backlink graph
page_sources   (page_id, source_id)                          -- provenance
agent_runs     (id, started_at, sources_in[], pages_touched[], model, summary)

agent_runs is your window into a hands-off system: "on run 47, Hermes read 3 sources and touched 5 pages." That log is how you stay hands-off without being blind.

Hermes reads new sources and proposes wiki edits — dry-run first (writes to a diff/log, not the live wiki). Watch a few runs before letting it auto-apply.

4

Let it run

Turn on auto-apply behind the tripwires + agent_runs log. Add pgvector/RAG so answers cite the base. Now it maintains itself.

win → hands-off, auditable, revertable

Honest cautions

This is a project / experiment, and an ungated autonomous agent is genuinely risky. The whole design is built so the risk is recoverable, not absent: immutable sources + rebuildable wiki + full history means the worst case is a re-run, never a loss.

Entity resolution is the part that will actually bite. Research on overlapping topics produces overlapping facts; without a stable page identity (canonical slugs/entities) the agent forks "Carotenoid" into three subtly different pages over time. Decide identity early.

Hermes orchestrates; it isn't the researcher. A small model is fine for extract / dedupe / cross-link, and underwhelming at genuine deep research — keep the heavy reasoning on capable OpenRouter models and the curation loop on the cheap one.

Watch it before you trust it. Run the agent in dry-run (phase 3) long enough to see its failure modes. Auto-apply is a decision you make after the tripwires have earned it.

The front end as a tiling window manager

Open question for the dashboard that reads this system: what if it behaves like a tiling window manager (i3 / yabai style) rather than a fixed page? Split the screen into panes, each showing one live view of the architecture above, arranged and resized on the fly. It fits this design unusually well — the pieces here are naturally several things you want to watch at once, side by side.

The model is small: a pane is either a leaf (one view) or a split with two children and a ratio — a BSP tree, the same structure a real tiling WM uses. Resize adjusts a ratio, splitting a pane replaces a leaf with a split, closing collapses the sibling up. It's plain JSON state and keyboard-driven, and (this is the point) it is 100% client-side — no SSR, no server runtime. So Next.js buys nothing here; it would only fight the current static-on-Cloudflare model. Two paths that don't:

PathWhatFit
Vanilla, single fileBSP tree + flexbox splits + drag-resize gutters + a keymap, a few hundred lines, no depsMatches the house style (self-contained index.html, links /style.css). Drops into /dashboard/ with no build step.
react-mosaicA React library that is a tiling BSP window manager; ships as one static Vite bundleFaster to something polished; keeps static hosting intact (one build artifact). The on-target pick if the pane logic gets rich.

The real design question isn't can it tile — it's what an addressable pane is. A WM tiles opaque OS windows; here each pane is a view of a first-class object in this system: a sources feed, a wiki page + its backlinks, a Hermes chat/research session, the agent_runs audit log. That last one is why this pairs naturally with Supabase Realtime — a pane can watch runs land as they happen, which is exactly the window you want into a hands-off system. Each pane resolves to a slug/route, so a whole layout is shareable and restorable as URL state.

Verdict: not a stretch — a genuinely good match for a dashboard whose job is to watch several live tiers at once. Keep it client-side; reach for react-mosaic only if a hand-rolled tree gets unwieldy. A pane contract (slug → view) is the thing to nail down first, not the tiling.

A design note, not a build. Supersedes the earlier hybrid personal-AI note (unRAID-hosted, human-PR-gated). Sequence subject to change once the first table is real and reality has opinions.
