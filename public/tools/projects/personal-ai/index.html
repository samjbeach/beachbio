personal infrastructure · design note

Hybrid personal AI — architecture

unRAID home server · Cloudflare Tunnel + Access · cloud research, local reading

One home server that turns research into something you can read, keep, and trust. Heavy reasoning is rented from the cloud (OpenRouter); reading and curation run locally (Kokoro, a small local model); and a knowledge base grows over time — but only through changes you approve. Everything sits behind a single identity gate, reachable from your phone or laptop without exposing anything raw to the internet.

Load-bearing decisions

the guardrail

The agent edits through pull requests, never live

Every change the curation agent makes to the wiki is a commit on a branch → a PR you merge. Diffable, revertable, and human-gated — the same branch→PR→merge rhythm the rest of this site already runs. It's the antidote to a knowledge base quietly rotting.

one front door

Everything behind one tunnel + Access

A single cloudflared tunnel publishes each service on its own subdomain, all behind the same Cloudflare Access app. You log in once; machine-to-machine calls use Access service tokens. Nothing is exposed directly to the internet.

cloud vs local

Rent reasoning, own the rest

A dumb policy table routes each task: deep research → OpenRouter (capable, per-use); summarize / curate / route → the local model (cheap, private, always-on); read aloud → local Kokoro. Be honest that a small local model can't do the research — it orchestrates.

frontend for free

The static site is the client

This site (already behind Access) is the control surface: the dashboard kicks off runs and browses reports; the Markdown reader tool just repoints at the local Kokoro endpoint to gain real per-word timestamps and phone-speed synthesis.

sequencing

Build a spine, not a big bang

Five services multiply failure modes. Stand up one capability at a time, each earning a concrete win before the next. The reader-on-local-Kokoro step alone is worth doing on its own.

git as memory

Reports and wiki are just repos

Research reports and the wiki are markdown in git — rendered by the same static-site muscle you already use. History is the audit log; a rollback is a revert.

What happens on a request

FlowPathNotes
Research Dashboard → Router → OpenRouter → save reports/*.md You ask a question; the router runs the deep-research prompt on a capable cloud model and commits the result as a report.
Read Reader → kokoro-fastapi → audio + word times → highlight The report (or any markdown) is synthesized locally; per-word timestamps drive exact highlighting. Fast on any device.
Curate Router → Ollama → branch on wiki/ → your PR A local pass cross-links the new report into the wiki, dedupes, fixes an index — and opens a PR for you to approve.

The spine — build order

1

Local Kokoro, reachable everywhere

unRAID + cloudflared + kokoro-fastapi behind Access. Repoint the Markdown reader tool at it.

win → fast, timestamped reading on any device, one new container
2

Generate a report

A dashboard action → router → OpenRouter → commit reports/*.md. The new report simply shows up in the reader.

win → research you can listen to, end to end
3

Wiki + curation agent (via PRs)

The curation pass cross-links reports into wiki/, opens a PR; you merge. Local model does the cheap work, OpenRouter the heavy.

win → a knowledge base that grows safely
4

Formalize the router

Once you've felt the cloud-vs-local calls by hand, encode them: n8n policy, schedules, retries, budgets.

win → it runs itself, on your terms

Honest cautions

Local models orchestrate; they don't research. A 7–8B Hermes is great for routing and summarizing and underwhelming at genuine deep research — keep that on OpenRouter and you won't be disappointed.

Always-on has a wattage. A 24/7 box (especially with a GPU for local inference) is real, recurring power draw versus OpenRouter's pay-per-use — the trade that matters more than it sounds.

The agent-maintained wiki is the risky bit. That's exactly why it's gated behind your PR review. Resist the urge to let it merge its own changes "just for the small ones."

Don't expose services raw. Kokoro and Ollama should only ever be reachable through the tunnel, behind Access — never a forwarded port.

A design note, not a build. Sequence subject to change once the first container is actually running and reality has opinions.
